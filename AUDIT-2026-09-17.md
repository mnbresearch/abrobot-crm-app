# Full-surface audit — 17 September 2026

Six specialist agents, one per feature area, each hunting the failure mode this
codebase keeps producing: **something that looks like success and isn't.**

That shape has three recurring causes, and almost every finding below is one of
them:

1. **`postgrest-js` resolves with `{ data: null, error }` — it does not throw.**
   So `await supabase.from(x).update(y)` swallows a refused write completely.
2. **PostgREST `max-rows` silently truncates at 1,000.** When the truncated
   value feeds a boolean, truncation does not shorten the answer, it *inverts*
   it.
3. **A signal written to a place nothing reads.** 2,502 cron failures sat in
   `cron.job_run_details` for eight days.

Counts: **8 blockers, 24 high, 41 medium, 18 low.**

## The eight blockers

### B1 — Buy one month of a higher plan, inherit the whole remaining term
`supabase/migrations/20260901090000_security_hardening.sql:71-80`

`grant_plan_from_payment` extends `current_period_end` from the existing value
*and* overwrites `plan`, with no comparison between them. Buy Starter annual
(₹9,990), then Business monthly (₹4,999), and you hold **13 months of Business
for ₹14,989 instead of ₹49,990.**

**₹35,001 lost per org, per exploit, through the normal UI.** No skill required.
The mirror case harms the customer: clicking a cheaper plan converts their
remaining paid months to the cheaper tier with no proration and no refund.

### B2 — A refund or chargeback never removes access
`supabase/functions/billing-webhook/index.ts:127-134`

No `REFUND_STATUS_WEBHOOK` branch, no dispute branch. And in `effective_plan`,
`subscriptions.status` is **selected and never read** — only `current_period_end`
decides entitlement, so setting `status='cancelled'` by hand revokes nothing.

Refund an annual Business order and the customer keeps **₹49,990 of plan** for
twelve months. Chargebacks behave identically: pay, get granted, charge back,
keep the plan.

### B3 — The AI agent reads the *oldest* 20 messages, never the recent ones
`supabase/functions/chat-agent/index.ts:399`

`.order("created_at")` defaults to ascending, so `.limit(20)` returns the
**first** 20 rows. Past turn 10 the model is fed a frozen window of the opening
exchange forever.

Invisible for short chats; guaranteed for long ones — i.e. it breaks exactly the
conversations that were about to convert. Reads as "the bot got dumb", so nobody
reports it as a bug.

### B4 — Four of the seven onboarding CTAs land on "Page not found"
`app/src/lib/router.ts:50-55`

`navigate()` stores the whole string including the query, and routing is exact
equality — so `/settings?tab=install` matches nothing. The topbar still says
**Settings** above a body saying **Page not found**, which reads as a broken
deploy on a brand-new customer's first session.

### B5 — "Email sent" when nothing was sent
`app/src/routes/LeadDetail.tsx:85-105`

`send-campaign` returns **HTTP 200** with `{sent: 0, errors: [...]}` when the
send fails. `callFunction` only throws on non-2xx, and the return value is
discarded. No activity row is written either, so the timeline shows nothing.

A counsellor tells a client "I've emailed you the documents." Nothing was sent.

### B6 — Nurture reports `ok` while 96% of sends fail
`supabase/functions/nurture/index.ts:356` → `:522`

Per-lead failures go into a local array returned in the HTTP body and read by
nothing. The heartbeat's `bad` count only catches orgs that *threw*. A run where
2,400 of 2,500 sends failed writes `last_status = 'ok'`.

The first post-restart run will 429 after ~100 emails (Resend free tier) and
report `ok, 100 sent, 0 failed`. Worse: a lead emailed but not step-advanced is
**re-emailed every run, forever**, while the job reports healthy.

### B7 — Nurture's oldest 100 leads starve everyone behind them
`supabase/functions/nurture/index.ts:248-260`

Due-ness is computed in JavaScript *after* the page is fetched, but the query
orders oldest-first with `limit(100)` and has no "is due" predicate. Leads stay
in the candidate set through their entire 72h/96h waiting windows.

An org with 300 overdue leads: leads 201–300 get their first email around
**4 October**. The run report says `considered: 100, sent: 0`.

### B8 — The webhook reconciler double-counts and auto-disables healthy endpoints
`supabase/migrations/20260906100000_prelaunch_hardening.sql:230-262`

`status_code is null` is the "not yet reconciled" sentinel — but a pg_net
*timeout* also has `status_code = NULL`. The reconciler writes NULL back, so the
row stays eligible and re-increments `failure_count` on **every 5-minute run**.

One customer endpoint that answers slowly is permanently disabled after ~100
minutes, and there is no UI to re-enable it (`Integrations.tsx:660-686` renders
no active badge and no resume button).

## Cross-cutting patterns

**Unchecked `{ error }` — 30+ sites.** Concentrated in `chat-agent` (6),
`nurture` (5), `lead-webhook` (4), `api` (3), and across the frontend. The
pattern is always the same: the write is skipped, the caller reports success.

**Metering is unchecked everywhere it matters.** Every `consume_usage` call in
`whatsapp-send`, `lead-webhook`, `send-campaign` and `nurture` discards the
result. The spend is real; only the counter is missing — so the cap silently
stops binding.

**`consume_usage` increments before it checks**, so refused actions still
consume. A capped org's meter climbs past its own limit and Settings shows
"7,132 / 5,000".

**Soft delete keeps leaking.** Fixed in `guard_lead_limit` and `usage_snapshot`
on 14 Sep; `org_assignment_load()` was missed, so archived leads still count as
open work and round-robin routes away from whoever cleans up.

**Empty state used as an error state — 6 screens.** Templates, Team,
Automations, Conversations, Admin's audit log, and the lead timeline all toast
an error that auto-dismisses in 3.2s, then show confident copy inviting the user
to create what they already have.

**Accessibility.** ~59 of 75 inputs have no programmatic label; `Modal` has no
`role="dialog"`, no focus trap and no focus restoration; list rows are
mouse-only across five screens; six colour pairs fail WCAG AA, including
`.pill-green` at **2.24:1**.

## What was verified as sound

Worth knowing where *not* to spend review time:

- **Cashfree signature verification** — HMAC-SHA256 over `timestamp + rawBody`,
  constant-time compare, raw body taken before parsing, fails closed on an unset
  secret. A forged webhook cannot grant a plan.
- **Replay/idempotency on payments** — `grant_plan_from_payment` uses a real
  compare-and-swap on `granted_at`. Replaying a captured webhook grants nothing.
- **Cross-tenant isolation** — org identity is never taken from the request on
  any path. `.or()` injection is closed at all four call sites. Money is never
  computed in floating point.
- **API key storage** — 32 random bytes, SHA-256 stored, raw value returned
  exactly once, never logged.
- **`lib/store.tsx`** — pagination, total ordering, de-duplication and the
  re-served-page-one guard are all correct. The strongest code in the repo.
- **The CSV import and export** — both pre-flight, both refuse rather than
  partially commit, both report honestly.
- **Unsubscribe** — unguessable token, GET renders and mutates nothing (so link
  scanners can't opt people out), the confirmation never lies about a zero-row
  update, RFC 8058 headers on both bulk paths.
- **`npx tsc --noEmit`** passes clean under `strict`.

## Suggested order

1. **B1, B2** — money leaving the business today. SQL only.
2. **B3, B4, B5** — one-line fixes, each visible to every customer.
3. **H2, H3, H4** — security: XSS on customer domains, cross-tenant WhatsApp
   billing, SSRF to cloud metadata.
4. **B6, B7** — before nurture restarts, or the restart itself causes the damage.
5. **H1, H5** — rate limiting on the two unauthenticated write surfaces.
6. The unchecked-`{error}` sweep, as one mechanical pass.
7. Frontend empty-vs-error states, then accessibility.
