# Full audit — 1 Sep 2026

Four parallel deep reviews (database security, edge-function security, silent
failures, product gaps) plus a live walk of the app. Everything below is
grounded in code I read or behaviour I observed, not a checklist.

**Read this first:** two findings are urgent. One lets a customer who has paid
once keep a paid plan forever, free. The other means **self-serve signup does
not work at all right now.**

---

# 1. Critical

## 1.1 Pay once, keep the plan forever — free

`grant_plan_from_payment(p_payment_id)` is `SECURITY DEFINER`, writes
`organizations.plan` and `subscriptions`, takes a caller-controlled id, does no
authorisation check, **and had no `REVOKE`.** Postgres grants `EXECUTE` to
`PUBLIC` by default, so PostgREST exposed it at
`POST /rest/v1/rpc/grant_plan_from_payment` to anonymous callers.

It is also not idempotent, despite a comment saying it is. It computes
`greatest(now(), current_period_end) + period_months`, so **every call adds
another month**.

The attack needs no special access: `payments_read` lets any active member read
their own org's payment rows, so the id is not secret. Pay ₹999 once, call the
endpoint 120 times, hold the plan for a decade. This defeats the entire expiry
system built last week.

The same class of bug was caught and revoked for `consume_usage` and
`mark_lapsed_subscriptions` in the enforcement migration. These two were missed.

**Fixed** in `20260901090000_security_hardening.sql`: revoked, plus real
idempotency via a `payments.granted_at` compare-and-swap. That also fixes an
honest-path bug — `billing-webhook` returns 500 on a failed grant so Cashfree
retries, and the retry used to double-extend the subscription.

## 1.2 Self-serve signup is broken — nobody can create an organisation

`guard_profile_changes()` blocks any `org_id` change unless the caller is a
super admin. `create_organisation()` and `accept_invite()` both have to move a
profile into an org — and `SECURITY DEFINER` does **not** change `auth.uid()`.
So the trigger sees an ordinary counsellor moving themselves and raises
*"Only a super admin can move a member to another organisation."*

Both functions therefore fail **100% of the time**. This landed when you applied
the self-serve signup migration. `CreateOrg.tsx:52` does surface the error, so
it fails visibly rather than silently — but anyone who signs up today is stuck
on that screen, and no invited teammate can join.

**Fixed.** The tempting patch is to loosen the guard, which is exactly what
would make 1.3 and 1.4 exploitable. Instead the two legitimate bootstrap paths
announce themselves with a transaction-local flag (`set_config(..., true)`)
that only `SECURITY DEFINER` code can set and which cannot leak into a later
client statement.

## 1.3 An org admin could mint a platform super admin

`invites_write` checks the org but says nothing about `role`, and
`accept_invite()` copies `inv.role` onto the profile verbatim. The UI dropdown
offers only counsellor and admin — irrelevant, PostgREST accepts whatever is
POSTed.

```
POST /rest/v1/invites {"org_id":"<mine>","email":"me+2@gmail.com","role":"super_admin"}
```

Accept it from the second address and you hold read/write on **every tenant on
the platform**. `guard_profile_changes` correctly blocks the direct route; the
invite path routed around it.

**Fixed:** CHECK constraint on the table plus a guard inside `accept_invite()`.

## 1.4 Join any organisation by editing your own email

`accept_invite()` matched on `prof.email` — the **`profiles` column**, not the
JWT, despite the comment claiming otherwise. `profiles.email` was user-writable
(`prof_own_update` has no `WITH CHECK`, and the trigger guarded `org_id`, `role`
and `status` but not `email`). Two requests:

```
PATCH /rest/v1/profiles?id=eq.<self>  {"email":"admin@targetcompany.com"}
POST  /rest/v1/rpc/accept_invite
```

You are inside their organisation. Combined with 1.3: org admin of a company
you have never met.

**Fixed:** identity now read from `auth.users`, and the trigger blocks email
edits.

## 1.5 The privilege guard did not run on INSERT

`trg_guard_profile_changes` was `BEFORE UPDATE` only. Every check it performs is
a transition check, so inserting a profile row instead of updating one bypassed
all of them. Whether that was exploitable depends on whether a permissive
self-insert policy exists on `profiles` — **which is not in any migration and I
could not verify** (see §5).

**Fixed regardless:** the trigger is now `BEFORE INSERT OR UPDATE`, and a new
profile may only be your own, unprivileged, and unattached to an org.

# 2. High — unauthenticated endpoints

These are **not fixed**; each needs a shared cron secret, which is a deploy
decision rather than a code change I should make unilaterally.

**`run-automations`, `nurture`, `system-health` and `summarize-chats` are all
deployed `--no-verify-jwt` and take the target org from the request body.**

- `run-automations` — `POST {"dry_run":true}` with **no** `org` returns lead
  names and automation rule names for **every tenant**. With an org slug it
  executes that tenant's automations for real against up to 5,000 records.
- `nurture` — `POST {"org":"victim"}` emails up to 200 of another tenant's
  leads, from your shared sending domain, and permanently advances their
  `nurture_step`.
- `system-health` — a GET with no `?org=` returns every org's status, including
  **which credentials each one has stored**. It also makes one live Groq call
  per tenant, so a single request fans out to N paid API calls.
- `summarize-chats` — the cheapest to abuse. `conversation_ids` is not
  deduplicated, so one request with the same id 150 times buys 19 Groq
  completions at 1,600 tokens each, unmetered, on the shared key. Loop it and
  you exhaust the quota that `chat-agent` depends on — taking the widget down
  for **every** customer at once.

Also unfixed and worth your attention:

- **`send-campaign` is an open mail relay.** `test_to` (line 78) sends
  attacker-controlled HTML with an attacker-controlled subject to **any address
  on the internet**, from your verified domain. Any active member, any role, no
  rate limit. Fix: require `test_to` to equal the caller's own email.
- **`send-campaign` selects `role` and never checks it** (line 67). Every active
  member, including a counsellor on a trial, can mass-mail 2,000 leads.
  `billing-checkout` does enforce `org_admin`; this one forgot.
- **`app-signup` fails open** when `APP_WEBHOOK_SECRET` is unset (`if (APP_SECRET && ...)`)
  — that is the deployment default. It also interpolates an unescaped `name`
  into an outbound HTML email.

# 3. Silent failures

Six fixed today, the worst first. This codebase has a documented history here —
five previous instances, all the same shape.

| Fixed | What the user saw | What happened |
|---|---|---|
| `chat-agent` lead insert | Normal reply, HTTP 200 | Insert rejected, enquiry gone, no alert, no trace |
| `nurture` unsubscribe | "You're unsubscribed" | Update failed or matched nothing; mail keeps coming |
| `billing-webhook` lookup | 200, Cashfree stops retrying | One DB blip = customer paid, plan never granted, permanently |
| `Import` rejected rows | "Rows with no contact: 400" | Plan limit hit; user edits a perfectly good CSV |
| `useLeads` failed read | "No leads yet" across 5 screens | One 503 tells a customer with 4,000 records they have none |
| `SetupChecklist` counts | Steps shown incomplete | 503 → told to redo work already done |

**Still open, ranked** (full list with line numbers in the audit trail):

1. `run-automations` / `run-actions` — every automation action write is
   unchecked, `automation_runs.ok` is written `true` regardless. A rule pointing
   at a deleted stage is indistinguishable from success.
2. `lead-webhook` dedupe path — the enquiry *text* lives only in an unchecked
   activity insert, then returns `ok:true`. Sender never retries.
3. `nurture` step advance — email sent, counter not saved, so the same email
   re-sends forever.
4. `Settings` pipeline save — "Pipeline saved" is unconditional; a mid-loop
   failure leaves duplicate `position` values.
5. `Import` duplicate detection — a failed read means every row is treated as
   new and the whole file is duplicated, reported as "Duplicates skipped: 0".
6. ~18 more reads rendering errors as legitimate empty states (Team, Templates,
   Automations, Activity, Conversations, Reports).

A lint rule banning bare `await supabase.from(x).insert|update|delete(...)`
without destructuring `error` would catch about two-thirds of these
mechanically. `supabase-js` never throws, so every `try/catch` around a query
in this codebase is dead code.

# 4. What the product is missing

The honest headline: **you cannot send anything from this CRM.**

`whatsapp-send` and `send-campaign` are fully built, authenticated and
plan-gated — and **no UI calls either one.** `Templates` is a notepad with no
Send button. `LeadDetail` offers `wa.me` / `tel:` / `mailto:` deep links that
open another app and log nothing.

That single gap undermines the pricing model: WhatsApp is what Growth (₹2,499)
and Business (₹4,999) are sold on, and right now **Growth buys a green pill in
Settings**. There is also no UI anywhere to enter WhatsApp credentials, so no
tenant could turn it on even if the button existed.

Three more that would embarrass you in a demo:

- **Mobile is broken, not unpolished.** `app.css:391` hides the sidebar below
  820px with **no replacement navigation**. The pipeline board uses HTML5 drag
  events, which do not fire on touch — the board is dead on a phone. Indian SME
  sales teams live on phones; every competitor ships an app.
- **Nurture is hardcoded to one tenant.** `nurture/index.ts:126` reads
  `let slug = "abrobot"`, and the email copy is hardcoded study-abroad. Every
  other customer's Settings shows "Automated follow-up emails" ticked, doing
  nothing. A dental clinic ticks a box that is a lie.
- **Two of six automation triggers can never fire.** `stage_changed` is offered
  in the UI, but every stage move happens client-side as a direct update, so
  nothing fires it. And `chat-agent` never calls `fireEventAutomations` — so
  the flagship "round-robin new records" recipe **does not apply to leads from
  your own AI widget**, the product's stated differentiator.

**Ranked next ten**, effort in brackets:

1. Send WhatsApp + email from the lead record, from a template, logged [S/M] —
   the backend already exists with zero callers. Best value-to-effort in the repo.
2. WhatsApp setup UI + thread view [M] — without it, nobody can enable #1.
3. Mobile: responsive nav, card lists, tap-to-move-stage, PWA [M].
4. Ownership: owner column, filter, "my leads", reassign-on-disable [S] — pure
   UI over the existing `assigned_to`. Today a disabled counsellor's leads sit
   invisible and still count in round-robin.
5. Fire automations on stage change and on chat/manual/import creation [S].
6. Industry-aware lead scoring [M] — currently every lead in 13 of 14 packs
   scores ~45 for the same reasons, and the Dashboard ranks work by it.
7. Repoint three server paths off the legacy `stage` enum to `stage_key` [S] —
   round-robin load, nurture eligibility and campaign audience are all silently
   wrong for every non-study-abroad tenant.
8. Make nurture multi-tenant, or hide the toggle [M].
9. Webhook keys UI + named integrations (website form, Facebook Lead Ads,
   IndiaMART) [S/M] — the Install tab already tells users to "create a key under
   webhook keys", a screen that does not exist.
10. Complete export + audit log [M] — export currently drops every custom field,
    tag, owner and note, i.e. all the vertical data. Audit is table stakes for
    hospitals and law firms.

**Do not build:** quotes/GST invoicing (Tally and Vyapar own it, and it drags in
e-invoicing compliance), native apps (PWA gets 90% for 15%), two-way mailbox
sync (months of work for a buyer who sells on WhatsApp — ship BCC-to-log
instead), a custom report builder (everyone asks, nobody uses), more industry
packs (fourteen is plenty; the gap is depth per pack), your own dialler, and
SSO/SAML/SOC 2 at this price point. A DPA and privacy policy before selling into
healthcare or legal is *not* in this category — that is paperwork you need.

# 5. What I could not verify

I need you to run one query. Three tables' policies exist only in the database,
not in any migration, and two of the answers change the risk picture materially.

```sql
select c.relname as table_name, pol.polname,
       case pol.polcmd when 'r' then 'SELECT' when 'a' then 'INSERT'
            when 'w' then 'UPDATE' when 'd' then 'DELETE' else 'ALL' end as cmd,
       pg_get_expr(pol.polqual, pol.polrelid)      as using_expr,
       pg_get_expr(pol.polwithcheck, pol.polrelid) as with_check_expr
  from pg_policy pol join pg_class c on c.oid = pol.polrelid
 where c.relname in ('organizations','profiles','webhook_keys')
 order by c.relname, pol.polname;
```

- **`organizations`** — if any policy lets a plain member UPDATE it, then
  `PATCH /organizations?id=eq.<own> {"plan":"enterprise"}` grants unlimited
  everything and every limit in the system evaporates. `plan`, `trial_*`,
  `credits_*` and `active` must be super-admin or service-role only.
- **`profiles`** — a permissive INSERT policy was the other half of 1.5.
- **`webhook_keys`** — these are bearer credentials. A counsellor who copies one
  keeps an unauthenticated write channel into the CRM **after being disabled**;
  revoking RLS does not revoke a copied token.

I also could not test tenant isolation with two real organisations, which
remains the single most valuable untested thing in this project. The Supabase
dashboard repeatedly dropped the project session today — every SQL editor
attempt bounced to the organisation list, and `nandadynastybuilders-2809` does
not appear among your orgs, consistent with the Vercel-managed-org permission
problem we hit earlier.

# 6. Known and accepted

- **`agent_config` holds API keys readable by any active member.** RLS is
  row-level, so a counsellor who can read the row reads `groq_api_key`,
  `resend_api_key`, `whatsapp_token`, `telegram_bot_token` and `app_secret`.
  `Settings.tsx` avoids selecting those columns — that is hygiene, not a
  control, and one curl bypasses it. **Currently latent: `system-health` reports
  "No counsellor accounts yet".** It stops being latent the day you hire one.
  The prepared migration blanks the columns and relies on the env fallbacks that
  already exist in every consumer. Rotate the keys when you do it.
- **Free-tier Supabase.** Production CRM, five tenants' live lead intake,
  payment webhooks, no SLA, projects pause after inactivity.
- **Prompt injection can extract an org's knowledge base** via the public chat
  widget. Inherent to the design; document it rather than pretend otherwise.
